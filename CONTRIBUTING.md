# Правила разработки

## Стандарты кодирования

### 1. Конфигурация
Все переменные окружения добавляются **только** в класс `Settings` (`app/core/config.py`).
- Секреты (ключи API, пароли) обязательно использовать с типом `SecretStr`.
- Для каждой новой переменной добавлять описание в `.env.example`.

### 2. Логирование
- Получение логгера **только** через `get_logger(__name__)` из `app/core`.
- Никаких `print()` в коде.
- Уровни:
  - `DEBUG` — детальная отладочная информация.
  - `INFO` — ключевые события (старт, завершение операций).
  - `WARNING` — неожиданные ситуации, которые не ломают работу.
  - `ERROR` — ошибки, требующие внимания.

### 3. Модели данных
- Все структуры данных, передаваемые **между пакетами** (`api`, `rag`, `llm`, `bot`), должны быть Pydantic-моделями из `app/models/`.
- Локальные модели внутри компонента допустимы, но наружу отдавать только модели из `app/models/`.

### 4. Взаимодействие компонентов
- Компоненты не должны обращаться напрямую к внутренним структурам друг друга.
- Взаимодействие только через согласованные интерфейсы.
- Любые изменения API-контрактов должны обсуждаться с командой и отражаться в `app/models/`.

### 5. Git workflow
- `main` — стабильная ветка.
- Для каждой задачи создаётся feature-ветка от `main`: `feature/api-layer`, `feature/rag-retriever`, `feature/llm-provider` и т.д.
- Слияние только через Pull Request после код-ревью.
- Все тесты должны проходить перед мёржем.

### 6. Тестирование
- Каждый компонент должен иметь модульные тесты.
- Интеграционные тесты для API.
- Перед коммитом прогонять `ruff check app/` и `pytest tests/`.
